좋아. 여기서는 **데이터 계약 관점**으로 정확히 나눠야 해.

현재 프로젝트는 Unreal이 `/api/game/ai/respond`로 플레이어 입력과 게임 상태를 보내고, AI 백엔드는 STT, Understanding, Level/Hint, NPC Dialogue, Validator를 거쳐 Unreal이 실행 가능한 JSON을 반환하는 구조야. 이 방향은 기존 프로젝트 문서의 “언리얼은 AI 내부 구조를 몰라도 되고, 백엔드는 검증된 command JSON만 반환한다”는 원칙과도 맞아.

# 0. 먼저 큰 역할 구분

```
Unreal
= 현재 게임 상황과 플레이어 입력을 보낸다.

STT Pipeline
= wav 음성을 text로 바꾼다.

Orchestrator
= 모든 데이터를 모아서 각 Agent/Controller에 전달한다.

Understanding Agent
= 플레이어 발화의 의미, 의도, 슬롯, 위험도, 감정을 분석한다.

English Level & Hint Agent
= 영어 수준, 실수 유형, 힌트, 추천 표현을 만든다.

Scenario State Machine
= 다음 노드를 Rule-based로 결정한다.

NPC Dialogue Agent
= NPC 대사와 피드백 문장을 만든다.

Validator
= 최종 response가 Unreal에서 안전하게 실행 가능한지 검사한다.
```

핵심은 이거야.

> **Understanding Agent는 “의미 해석”만 한다.Level/Hint Agent는 “학습 평가와 도움”을 한다.Scenario State Machine은 “다음 노드 결정”을 한다.**
>

# 1. 변수 소유권 표와 각 변수가 필요한 이유

아래 표는 개발자 C 기준으로 **누가 만들고, 누가 쓰고, 왜 필요한지**를 정리한 거야.

## 1-1. 요청/세션 관련 변수

| 변수 | 생성/소유 | 소비 | 왜 필요한가 |
| --- | --- | --- | --- |
| `request_id` | Unreal 또는 Backend | Orchestrator, Logger | 요청 하나를 추적하기 위한 ID. STT 실패, Agent 실패, Validator 실패를 로그에서 추적할 때 필요 |
| `session_id` | Unreal | Orchestrator, 모든 Agent | 한 플레이어의 입국심사 세션을 구분. retry_count, risk_score, completed_intents 같은 누적 상태와 연결 |
| `player_id` | Unreal | Orchestrator, Logger | 유저 식별용. MVP에서는 닉네임 정도로도 충분하지만, 나중에 사용자별 학습 기록 저장에 필요 |
| `chapter_id` | Unreal | Orchestrator, OpenKB | 현재 챕터가 `CHAPTER_0_IMMIGRATION`인지 확인. 이후 식당/수하물 챕터 확장 시 필요 |
| `scene_id` | Unreal | Orchestrator, Validator | 현재 씬이 `JFK_IMMIGRATION_HALL`인지 확인. 존재하지 않는 씬 명령 방지 |
| `current_node_id` | Unreal | OpenKB, Understanding, State Machine | 가장 중요. 현재 질문이 방문 목적인지, 체류 기간인지, 숙소인지 알아야 의도 판정 가능 |
| `npc_id` | Unreal | NPC Dialogue, Validator | 어떤 NPC가 말하는지 식별. 예: `OFFICER_MILLER` |
| `last_npc_message` | Unreal | Understanding, NPC Dialogue | 플레이어 답변이 어떤 질문에 대한 답인지 판단할 때 필요 |

---

## 1-2. 입력/STT 관련 변수

| 변수 | 생성/소유 | 소비 | 왜 필요한가 |
| --- | --- | --- | --- |
| `input_type` | Unreal | STT Pipeline, Orchestrator | 입력이 `text`인지 `voice`인지 구분. text면 STT 생략, voice면 STT 실행 |
| `audio_file` / `wav_file` | Unreal | STT Pipeline | 플레이어 음성 원본. STT에서만 사용하고 Understanding Agent에는 직접 넘기지 않는 게 좋음 |
| `audio_mime_type` | Unreal | STT Pipeline | `audio/wav`인지 확인. 잘못된 포맷 처리에 필요 |
| `audio_duration_ms` | Unreal 또는 STT | STT, Logger | 너무 짧거나 긴 음성 감지. 예: 0.2초면 실수 입력일 수 있음 |
| `sample_rate_hz` | Unreal 또는 STT | STT | STT 품질 확인용. 필수는 아니지만 디버깅에 좋음 |
| `language_hint` | Unreal | STT, Understanding | `ko-KR`, `en-US`, `ko_en_mixed` 등. 콩글리쉬 모드에서 STT와 의미 분석 안정화 |
| `player_text` | Unreal 또는 STT | 모든 Agent | 최종 표준화된 플레이어 발화. text 입력이면 원문, voice 입력이면 STT 결과 |
| `stt_confidence` | STT | Orchestrator, Understanding, Level/Hint | STT 결과 신뢰도. 낮으면 “다시 말해 주세요” fallback 판단에 사용 |
| `stt_needs_repeat` | STT | Orchestrator, State Machine | 음성 인식이 불안정해 의미 분석 전에 재입력을 요구할지 판단 |
| `stt_warnings` | STT | Logger, Handoff Debug | 소음, 무음, 너무 짧은 음성 등 디버깅용 |

중요한 원칙:

```
wav 파일은 STT Pipeline까지만 간다.
Understanding Agent는 raw wav를 직접 다루지 않는다.
Understanding Agent는 STT가 만든 player_text만 분석한다.
```

| --- | --- | --- | --- |

| `npc_question` | OpenKB | Understanding | 플레이어 답변이 어떤 질문에 대한 답인지 비교하기 위해 필요 |
| `objective_kr` | OpenKB | Unreal UI, Response Builder | 현재 목표 UI 표시. 예: `방문 목적을 말하기` |

| `required_slots` | OpenKB / B | Understanding | 현재 노드에서 반드시 추출되어야 하는 정보 |
| `risk_keywords` | OpenKB / B | Understanding | `forever`, `illegal`, `secret` 같은 위험 표현 감지용 |
| `recommended_expression` | OpenKB / B | Level/Hint, NPC Dialogue | 추천 표현 생성의 기준. 예: `I'm here for travel.` |
| `base_hint_kr` | OpenKB / B | Level/Hint | 기본 힌트 문구. Level/Hint Agent가 사용자 맞춤형으로 변형 |
| `retry_question` | OpenKB / B | NPC Dialogue, State Machine | 애매한 답변일 때 재질문 문장으로 사용 |
| `allowed_next_nodes` | OpenKB / Unreal | State Machine, Validator | AI가 허용되지 않은 노드로 이동시키지 못하게 하는 안전장치 |

추천 방식:

```
Unreal이 보낸 allowed_next_nodes
+
OpenKB의 allowed_next_nodes

둘 다 확인하는 것이 안전하다.
```

예를 들어 Validator에서는 이렇게 판단하면 좋아.

```
next_node_id는 OpenKB allowed_next_nodes 안에 있어야 한다.
Unreal이 client_allowed_next_nodes를 보냈다면, 그 안에도 있어야 한다.
```

# 2. Unreal에서 wav 파일과 함께 보내야 하는 데이터

## 2-1. 추천 방식: `multipart/form-data`

음성 입력은 JSON만으로 보내기 어렵기 때문에, 프로토타입에서는 이 방식이 제일 현실적이야.

```
POST /api/game/ai/respond
Content-Type: multipart/form-data
```

보내는 필드:

```
audio: player_voice.wav
payload: JSON string
```

즉, `audio`에는 wav 바이너리 파일, `payload`에는 현재 게임 상태 JSON을 넣는다.

## 2-3. Orchestrator에게 필요한 입력 데이터

Orchestrator는 단순히 player_text만 받으면 부족해.

**전체 흐름을 조립해야 하므로 아래 정보가 필요해.**

| 데이터 | 필요 이유 |
| --- | --- |
| `request_id` | 전체 요청 추적 |
| `session` | 현재 플레이 세션, 노드, 씬 확인 |
| `npc` | 직전 NPC 질문과 speaker 정보 확인 |
| `player_input` | text인지 voice인지 구분 |
| `audio` | voice 입력일 경우 STT 실행 |
| `player_profile` | 콩글리쉬 모드, 영어 자신감 반영 |
| `player_state` | stress/confidence 등 상태 UI 업데이트에 활용 |
| `game_state` | risk_score, retry_count, completed_intents 반영 |
| `client_allowed_next_nodes` | Validator에서 노드 이동 안전성 확인 |
| `client_context` | 플랫폼/로케일/빌드 디버깅 |

Orchestrator는 이 데이터를 받아서 내부적으로 이렇게 바꿔.

## 2-5. Understanding Agent 입력 필수/선택 구분

| 필드 | 필수 | 이유 |
| --- | --- | --- |
| `current_node_id` | O | 어떤 질문에 대한 답인지 판단 |
| `player_text` | O | 분석 대상 발화 |
| `npc_question` | O | 답변 relevance 판단 |
| `success_intents` | O | 현재 노드 성공 의도 확인 |
| `required_slots` | O | 필요한 정보가 추출됐는지 확인 |
| `risk_keywords` | O | 위험 표현 감지 |
| `risk_score` | O | 누적 위험도 판단 보조 |
| `retry_count` | O | 반복 실패 상황 인지 |
| `chaos_konglish_mode` | O | 콩글리쉬 허용 여부 |
| `stt_confidence` | 선택 | voice 입력일 때 분석 신뢰도 보정 |
| `language_detected` | 선택 | ko/en mixed 처리 보조 |
| `completed_intents` | 선택 | 이미 통과한 항목 확인 |
| `player_state` | 선택 | stress 높을 때 emotion 보정 가능 |

    "konglish_interpretation_kr": "Travel이요는 여행 목적으로 왔다는 의미입니다.",

왜 필요한가:

| 데이터 | Level/Hint에서 쓰는 이유 |
| --- | --- |
| `player_text` | 문법, 어휘, 문장 길이 평가 |
| `intent_success` | 의미 전달 점수 산정 |

## B. Scenario State Machine에게 넘기는 데이터

Scenario State Machine은 Agent가 아니라 Rule-based야.

따라서 필요한 데이터는 더 적고, 명확해야 해.

```json
{
  "current_node_id": "IMM_002_PURPOSE",
  "understanding": {
    "intent": "visit_purpose_travel",
    "intent_success": true,
    "risk_delta": 0,
    "risk_tags": [],
    "extracted_slots": {
      "visit_purpose": "travel"
    },
    "missing_slots": [],
    "needs_clarification": false
  },
  "game_state": {
    "risk_score": 0,
    "retry_count": 0,
    "completed_intents": [
      "passport_submit"
    ]
  },
  "node_context": {
    "success_intents": [
      "visit_purpose_travel",
      "visit_purpose_vacation",
      "visit_purpose_visit_friend"
    ],
    "required_slots": [
      "visit_purpose"
    ],
    "allowed_next_nodes": [
      "IMM_003_DURATION",
      "IMM_002_RETRY_PURPOSE",
      "IMM_EXTRA_001_CLARIFY_PURPOSE",
      "END_BAD_HANDCUFF"
    ]
  }
}
```

왜 필요한가:

| 데이터 | State Machine에서 쓰는 이유 |
| --- | --- |
| `current_node_id` | 현재 노드별 transition rule 선택 |
| `intent_success` | 성공 여부 판단 |
| `intent` | success_intents에 포함되는지 확인 |
| `extracted_slots` | 필수 정보가 있는지 확인 |
| `missing_slots` | retry/clarify 판단 |
| `risk_delta` | 누적 위험도 계산 |
| `risk_tags` | 특정 위험 분기 판단 |
| `needs_clarification` | 재질문 노드 선택 |
| `retry_count` | 반복 실패 시 extra question 또는 retry 종료 |
| `allowed_next_nodes` | 안전한 노드 범위 제한 |

예시 rule:

```
if risk_score + risk_delta >= 7:
    next_node_id = END_BAD_HANDCUFF

elif intent_success == true:
    next_node_id = next success node

elif retry_count < 2:
    next_node_id = retry node

else:
    next_node_id = clarify node
```

## C. NPC Dialogue Agent에게 넘기는 데이터

NPC Dialogue Agent는 대사를 생성해야 하므로, Understanding 결과 중 **의미/감정/위험/콩글리쉬 정보**가 중요해.

```json
{
  "player_text": "Travel이요. Trouble 아니에요.",
  "node_context": {
    "node_id": "IMM_002_PURPOSE",
    "npc_question": "What is the purpose of your visit?",
    "retry_question": "Are you here for travel, business, or something else?"
  },
  "understanding": {
    "intent": "visit_purpose_travel",
    "intent_success": true,
    "meaning_summary_kr": "플레이어는 여행 목적으로 방문했다고 말했습니다.",
    "konglish_detected": true,
    "emotion": "nervous_humor",
    "risk_delta": 0,
    "needs_clarification": false
  },
  "level_hint": {
    "english_level": "beginner",
    "recommended_expression": "I'm here for travel.",
    "hint_kr": "의미는 잘 전달됐어요. 더 자연스럽게는 짧은 문장으로 말하면 됩니다."
  },
  "branch": {
    "branch_type": "success",
    "next_node_id": "IMM_003_DURATION"
  }
}
```

왜 필요한가:

| 데이터 | NPC Dialogue에서 쓰는 이유 |
| --- | --- |
| `intent_success` | NPC가 넘어갈지, 다시 물을지 톤 결정 |
| `meaning_summary_kr` | 피드백 문장 근거 |
| `konglish_detected` | 코믹하지만 친화적인 반응 생성 |
| `emotion` | NPC 표정/말투 선택 |
| `risk_delta` | 경고 톤 또는 serious tone 선택 |
| `needs_clarification` | 재질문 대사 생성 |
| `branch_type` | 성공/재시도/배드엔딩에 맞는 대사 생성 |
| `recommended_expression` | 피드백 문장에 포함 |

## OpenKB에서 붙여야 하는 것

```
- npc_question

```

- emotion

- risk_tags

## 다음 단계로 넘겨야 하는 것

```
To Developer B:
player_text + node_context + understanding + player_profile + game_state

To Scenario State Machine:
current_node_id + intent_success + slots + risk_delta + retry_count + allowed_next_nodes

To Developer A:
player_text + understanding + level_hint + branch + node_context
```

한 줄로 정리하면:

> **Unreal은 “상황과 입력”을 보내고, STT는 “음성을 텍스트”로 바꾸고, Understanding Agent는 “그 텍스트의 의미 신호”를 만들고, 이후 Agent/Controller들은 그 신호를 기반으로 힌트·분기·NPC 반응을 만든다.**
